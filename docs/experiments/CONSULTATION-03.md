Date: 2026-09-30. Status: **DONE; LOCAL/MOCKED AND THREE-SERVICE LIVE CONVERSATION VERIFIED; FINAL GEMINI-TO-GPU DEMO REHEARSAL PENDING**.

## Implemented boundary

`CONSULTATION_PROVIDER=deterministic` retains the CONSULTATION-02 structured form and its deterministic provider. `CONSULTATION_PROVIDER=gemini` changes only the consultation preference/recommendation stage. `GET /consultations/mode` tells the existing page which experience to show. `POST /consultations/{id}/turn` serializes a short text conversation in the existing bounded consultation store, updates structured preferences, and returns either `more_information` with one assistant question or `ready_for_recommendation` with three backend-validated recommendations. On an invalid or failed provider result, no messages, preferences, or recommendations from that turn are committed. The existing sequential generation cards, feature dispatcher, Hair/Makeup/Nails handlers, unified Kaggle worker and Custom routes are unchanged.

The SDK request uses `gemini-3.5-flash-lite` by default, configurable with `CONSULTATION_GEMINI_MODEL`. `GEMINI_API_KEY` is read only by FastAPI. Calls have one SDK attempt, 30-second HTTP timeout and 35-second outer timeout. There is no silent deterministic fallback. The installed Google GenAI SDK is pinned to `google-genai==2.7.0`. The SDK's documented default retry behavior is overridden with `HttpRetryOptions(attempts=1)`. Its full `response_json_schema` field is used because the strict Pydantic contract's `additionalProperties` is rejected by the API's narrower `response_schema` field. Backend Pydantic and the existing recommendation validator remain authoritative.

Only primary service, prior text messages, current structured preferences, the latest user text and compact eligible style IDs/names/tags/descriptions are sent to Gemini. No photo or generated image, price/duration, adapter, prompt, model path, Kaggle credential or internal path is included. Gemini may propose `status`, `assistant_message`, preference fields and style choices/reasons/complements. The backend validates exactly three distinct active primary styles, feature/style pairing, exclusions and complements; then attaches authoritative names, demo-only PHP price/duration and Nails model/renderer metadata. Complementary images are not generated.

## Makeup eligibility diagnosis, 2026-09-30

Read-only local catalog reconstruction (no Gemini or GPU request) found all three proposed IDs in the actual central Makeup style route, with `trained_preset` status and Consultation tags. With empty pre-answer preferences, all ten Makeup styles, including these three, are eligible and are included in the catalog payload sent to Gemini. The route then merges the provider's preference proposal and recomputes candidates before calling the validator. The rejected turn did not save those proposed preferences, so their exact values are unavailable after the fact.

Using the stated avoid phrases `heavy makeup` and `dramatic eye makeup` as the reconstructed post-answer preferences, candidate filtering reduced Makeup from ten to eight styles. `no_makeup_makeup` and `natural_makeup` became ineligible; `matte_nude` stayed eligible. Filtering splits the avoid phrases into individual words, including generic `makeup`, and matches any such word against style names/tags. The first proposed choice was `no_makeup_makeup` (display name `No-Makeup Makeup`), so **it is the first offending ID under this reconstruction**. This is a same-turn pre/post eligibility mismatch, not an invented or disabled style and not a validator malfunction. The precise provider-extracted avoid strings were not logged; therefore the individual ID rejected in the actual live turn cannot be independently proven from retained evidence. A later fix should make avoidance matching phrase/context aware so `heavy makeup` does not exclude a light style solely because its name contains `Makeup`, while retaining backend revalidation. No fix was implemented in this diagnosis.
